# Story 8.7: Cost Calculation from Pricing Table

## Description

MiniRouter tracks token counts but assigns no monetary value to them. A search for
`cost`/`price`/`pricing` across `*.cs` and `frontend/src` returns nothing. Operators can see
that a provider consumed 2M tokens; they cannot see what it cost, or which provider is cheapest
for a given workload.

9Router calculates cost per request from a static pricing table
(`docs/reff/open-sse/providers/pricing.js`) with three tiers of lookup and user-overridable
rates.

Cost here is explicitly a **tracking and comparison figure, not a billing figure**. The
reference is clear on this distinction and we should be too — MiniRouter does not charge anyone,
and its numbers will drift from provider invoices.

## Priority

3 (Wave 2 — fully independent; can land in any wave with slack)

## Implementation Steps

### 1. Pricing table

Static, compile-time, per million tokens, with separate input and output rates. Follow the
reference's three-tier lookup (`pricing.js`):

1. **Exact model match** — `gpt-4o-mini` → specific rates
2. **Pattern match** — regex/prefix, so `gpt-4o-*` variants resolve without an entry each
3. **Provider default** — fallback rate for an unknown model on a known provider

Unmatched → cost `null`, **not** zero. A null cost is honestly unknown; a zero cost silently
understates spend and corrupts any aggregate built on it.

Keep the table as a static array of records in `Services/PricingTable.cs`. Do not model it as
serializable configuration — that would add types to `AppJsonContext` for data that never
crosses a JSON boundary.

### 2. Cost calculation

```
cost = (input_tokens / 1_000_000 × input_rate) + (output_tokens / 1_000_000 × output_rate)
```

Use `decimal`, not `double`. Repeated `double` accumulation across millions of log rows
introduces drift that will show up in aggregates.

Calculate at log-write time in `Services/ProxyService.cs`, not at query time. Rates change; a
row's cost should reflect the rate in effect when the request was made.

### 3. Persist on the log row

Add to `request_log` (`Services/LogService.cs:23-39`) following the existing hand-rolled
migration pattern (`ALTER TABLE ... ADD COLUMN` wrapped in the try/catch that swallows
`SqliteErrorCode == 1`):

- `cost REAL` — nullable
- `cost_estimated INTEGER` — true when derived from Story 8.4's estimated tokens

**The `cost_estimated` flag is load-bearing.** Story 8.4 introduces estimated token counts for
providers that report no usage. Cost derived from an estimate is a guess built on a guess, and
mixing those into a spend total without a marker would mislead. If 8.4 has not landed, default
the column to false.

### 4. Analytics

Extend `GET /api/analytics/tokens` and `/api/analytics/keys` with `totalCost` and
`estimatedCostPortion`. Both queries are currently unbounded over all history
(gap analysis section 4) — leave that as is; adding date-range filtering is separate work.

### 5. Dashboard

Show cost alongside tokens in `frontend/src/Analytics.svelte`, with estimated portions visually
distinguished.

**While in this file, fix gap analysis defect 5:** `Analytics.svelte:105` reads
`item.requestCount`, but the API sends `totalRequests` (`Models/RequestLog.cs:23`). Total
Requests currently renders 0 always.

## Required Tests (QA)

- Lookup precedence: exact beats pattern beats provider default
- Unknown model → null, and null costs excluded from (not zeroed into) aggregates
- Calculation correctness against hand-computed fixtures
- `decimal` precision across a large accumulation
- Migration: pre-existing rows get null cost and remain queryable
- `cost_estimated` propagates from Story 8.4's `estimated` flag
- Frontend: Total Requests renders the API's `totalRequests`

## Notes

Pricing drifts. This table is a point-in-time snapshot and will be wrong within months — the
README should say so plainly rather than implying the figures are authoritative.

The reference supports user-overridable rates via a `pricingRepo` and a settings page. That is
deliberately **out of scope** here: it needs a table, an API, and UI, which roughly doubles the
story. Revisit only if the static table proves insufficient in practice.

Deliberately **not** included: budget limits, spend alerts, or per-key quotas. Those are
policy-enforcement features, not observability, and belong in their own epic.
