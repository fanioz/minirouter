# Story 8.5: Provider to Connection Split

## Description

MiniRouter allows exactly **one** credential per provider — `Provider.ApiKey`
(`Models/Provider.cs:9`). When that key hits a rate limit, the provider is out of rotation
entirely, even if the operator holds three other valid keys for the same upstream.

9Router separates the two concepts:

- **Provider** = a *type* definition. Endpoint, format, auth scheme, model list. No secrets.
- **Connection** = one *credential instance* — a row in `providerConnections` carrying
  `priority`, `isActive`, `lastUsedAt`, `consecutiveUseCount`, `backoffLevel`, `lastError`.

Multiple connections per provider is the multi-account feature. It is also the prerequisite for
account-level rotation, per-credential circuit breaking, and per-credential quota tracking.

This story also folds in the `providers.json` → SQLite migration (gap analysis Tier 2 item 4),
because the connection table has to live somewhere and migrating twice is waste.

## Implementation Steps

### 1. Schema

Move provider config out of `providers.json` into SQLite (`minirouter.db`, already present for
logs and keys):

```
providers      id TEXT PK, name, base_url, enabled, model, models TEXT(json),
               supports_stream_options, reports_stream_usage
connections    id TEXT PK, provider_id TEXT NOT NULL, name, api_key,
               priority INTEGER, is_active INTEGER, last_used_at TEXT,
               consecutive_use_count INTEGER, backoff_level INTEGER,
               last_error TEXT, error_code TEXT
```

Index `connections` on `provider_id` and `(provider_id, is_active)`, matching the reference's
access pattern (`docs/reff/src/lib/db/schema.js`).

Adopt the reference's **indexed-scalars-plus-JSON-blob** pattern for anything not queried.
This matters more for us than for Node: every distinctly-shaped serialized type grows the
source-generated `AppJsonContext`, which is compiled weight in the AOT binary.

### 2. Migration from providers.json

One-time, on startup, when `providers.json` exists and the `providers` table is empty:

- Each existing provider becomes one provider row plus **one** connection row
- Connection inherits the provider's `ApiKey`, gets `priority = 0`, `is_active = 1`
- Rename the source file to `providers.json.migrated` rather than deleting it
- Log the migration explicitly at startup

Do not delete the source. If migration is wrong, the operator's credentials are in that file
and nowhere else.

### 3. Selection strategy

Port from `docs/reff/src/sse/services/auth.js:27`. Two strategies:

| Strategy | Behavior |
|---|---|
| `fill-first` (default) | Highest-priority active connection first |
| `round-robin` | Sticky by `last_used_at` + `consecutive_use_count` vs a sticky limit (default 3), then least-recently-used |

Guard selection with a process-level mutex (`auth.js:9` uses `selectionMutex`). Without it,
concurrent requests read the same `last_used_at` and both pick the same connection, collapsing
round-robin into fill-first under load.

Note the existing round-robin over *providers*
(`ProviderService.GetNextProviderAsync:251`) is a separate concern and stays. This adds a second
rotation layer *within* a provider. Two nested rotations is what the reference does, and the
interaction needs explicit tests.

### 4. Re-key circuit state

Change `CircuitState` keys from `{providerId}::{modelName}` to `{connectionId}::{modelName}`
(`Services/ProviderService.cs:280`). A rate-limited key must not remove the provider's other
credentials from rotation — that is the entire point of the story.

Story 8.3's `BackoffLevel` moves onto the connection row so it survives restart. Currently it is
in-memory only.

### 5. Exclude exhausted connections during failover

Extend the existing `excludeProviderIds` retry mechanism to `excludeConnectionIds`, so a failed
request retries against a sibling connection before falling through to a different provider.
Order: sibling connections first, then other providers.

### 6. API and dashboard

- `GET/POST/PUT/DELETE /api/providers/{id}/connections`
- Provider responses include a connection count and aggregate health, not raw keys
- Masking stays per connection (`***last4`)
- Dashboard: nested connection list under each provider, with priority reorder and per-connection
  enable/disable

## Acceptance Criteria

- [ ] An existing `providers.json` migrates to one provider + one connection each, with no behavior change
- [ ] The source file is preserved as `providers.json.migrated`
- [ ] A provider accepts N connections via the API
- [ ] `fill-first` selects the highest-priority active connection
- [ ] `round-robin` rotates with the sticky limit honored, and does not collapse under concurrency
- [ ] A rate-limited connection is excluded while its siblings continue serving
- [ ] Circuit state is keyed per connection, not per provider
- [ ] `backoff_level` survives a process restart
- [ ] Failover prefers sibling connections before other providers
- [ ] Connection keys are masked in all API responses
- [ ] Existing provider CRUD API remains backward compatible

## Required Tests (QA)

- Migration: fresh DB + existing `providers.json` → correct rows, file renamed, idempotent on
  second startup
- `fill-first`: priority ordering, inactive connections skipped
- `round-robin`: sticky limit, LRU ordering, and **concurrent** selection producing an even
  distribution (the mutex test — mirrors the existing 300-call concurrency test in
  `ProviderServiceTests`)
- Circuit isolation: one connection open, siblings still eligible
- Failover ordering: sibling connections exhausted before other providers
- Restart persistence: `backoff_level` reloaded
- Regression: Story 7.1 comma-separated fallback and Story 8.3 backoff both still behave

## Notes

**This story widens the credential surface on endpoints that have no authentication.** The gap
analysis rates the open admin surface as Critical (`docs/reports/9router-gap-analysis.md`
section 9). `POST /api/providers/{id}/connections` on an unauthenticated, all-interfaces bind
lets anyone add a credential or read connection health. Dashboard auth should land before this
story, not after.

The reference's `providerSpecificData` JSON blob per connection is worth mirroring for
forward flexibility, but keep it genuinely opaque — do not add typed fields to
`AppJsonContext` speculatively.
