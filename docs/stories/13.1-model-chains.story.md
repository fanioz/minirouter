# Story 13.1: Model Chains (Named Fallback Sequences)

## Status

**Done**

## Story

As a MiniRouter operator,
I want to define a named model chain like `tier1` that maps to an ordered sequence of `providerId/modelId` targets,
So that callers can use a single stable model name and MiniRouter automatically falls back through the sequence on failure.

## Background

MiniRouter already has comma-separated explicit routing: `model: "provA/m1,provB/m2"`. That works, but the caller must know internal provider IDs, it's verbose, and it isn't manageable through the UI. Model chains are named aliases for pre-defined ordered sequences, stored in `model_chains.json`, manageable via the Chains UI tab, and discoverable via `/v1/models`.

The routing semantics are identical to the existing explicit waterfall loop in `ProxyService.ExecuteCompletionAsync` — model chains reuse that exact code path after resolving the name to a target list.

## Acceptance Criteria

1. `GET /api/model-chains` returns all chains; protected by `ApiKeyEndpointFilter`.
2. `POST /api/model-chains` creates a chain; `400` if `name` empty, contains `/`, or already exists.
3. `PUT /api/model-chains/{name}` updates description or models; `404` if not found.
4. `DELETE /api/model-chains/{name}` removes a chain; `404` if not found.
5. `POST /v1/chat/completions` with `model: "tier1"` executes the chain's targets as a waterfall — fallback only on 5xx/429; stop on success or 4xx (except 429).
6. If all chain members fail or are circuit-open, the last upstream error is returned (same as existing explicit routing behavior).
7. Chain name `tier1` appears in `GET /v1/models` as `{ "id": "tier1", "object": "model", "owned_by": "chain" }`.
8. `model_chains.json` is written atomically (temp-file + rename) — same pattern as `providers.json`.
9. Chains UI tab lists all chains with: name, description, member count, expandable ordered target list.
10. UI supports create, edit (description + models only; name is read-only post-create), and delete with confirm.
11. All new and existing tests pass; `dotnet build` clean; `npm run build` clean.

  /// Executes an ordered list of "providerId/modelId" targets as a waterfall.
  /// Falls through only on 5xx or 429; stops on success or any other 4xx.

- [x] 4.3 Add chain resolution at the **top** of `ExecuteCompletionAsync`, before the `/` check:
  ```csharp
  public async Task<ProxyExecutionResult> ExecuteCompletionAsync(ProxyExecutionRequest request, CancellationToken ct = default)
  {
      if (string.IsNullOrEmpty(request.RequestedModel))
          return new ProxyExecutionResult { Success = false, StatusCode = 400, ErrorMessage = "Model must be specified." };

      // Model chain resolution — must come before the '/' check
      var chain = _chainService.GetChain(request.RequestedModel);
      if (chain != null)
      {
          if (chain.Models == null || chain.Models.Count == 0)
              return new ProxyExecutionResult { Success = false, StatusCode = 400, ErrorMessage = $"Model chain '{chain.Name}' has no targets configured." };

          return await ExecuteExplicitChainAsync(chain.Models, request, ct);
      }

      // Existing: explicit routing (contains '/')
      if (request.RequestedModel.Contains('/'))
      {
          var targets = request.RequestedModel.Split(',', StringSplitOptions.RemoveEmptyEntries | StringSplitOptions.TrimEntries);
          return await ExecuteExplicitChainAsync(targets, request, ct);
      }

      // Existing: round-robin
      return await HandleRoundRobinExecutionAsync(request.RequestedModel, request, ct);
  }
  ```

> **Dev Note:** `_chainService.IsChain(name)` / `GetChain(name)` must be O(1) or O(n) over a typically small chains list — not a bottleneck. Using `GetChain` directly avoids double lookup. A chain name never contains `/` (validated on creation) so there is no ambiguity with the next check.

> **Dev Note:** The model name in the outgoing request body is rewritten to `targetModelName` inside `ExecuteSingleProviderAsync` (line ~455 of ProxyService.cs: `rootObj["model"] = targetModelName`). The caller never sees the chain name forwarded upstream — this is already handled correctly by the existing code.

## Dev Notes

### Routing Dispatch Priority

The three routing modes in `ExecuteCompletionAsync`, in evaluation order:

| Priority | Condition | Action |
|---|---|---|
| 1 | `IsChain(requestedModel)` == true | Resolve chain → `ExecuteExplicitChainAsync` |
| 2 | `requestedModel.Contains('/')` | Split on `,` → `ExecuteExplicitChainAsync` |
| 3 | Neither | `HandleRoundRobinExecutionAsync` |

Chain resolution is checked **before** the `/` check to allow future chains with slashes in names (not in scope), and because `IsChain` is O(n) on a small list — typically < 20 chains, negligible.

### `ExecuteExplicitChainAsync` — Extracted from existing code

This is a **pure refactor** of the existing block. The behavior is identical; the only change is the code now lives in a named method callable from two places. The existing comma-separated explicit routing path (`model: "provA/m1,provB/m2"`) now calls `ExecuteExplicitChainAsync` instead of having inlined logic. The call site becomes:

```csharp
// Before (inlined):
if (request.RequestedModel.Contains('/'))
{
    var targets = request.RequestedModel.Split(',', ...);
    // 40 lines of loop logic
}

// After (extracted):
if (request.RequestedModel.Contains('/'))
{
    var targets = request.RequestedModel.Split(',', ...);
    return await ExecuteExplicitChainAsync(targets, request, ct);
}
```

This refactor has zero behavior change and is covered by existing tests.

### Model Field Rewriting — No Changes Needed

`ExecuteSingleProviderAsync` already rewrites `reqBody["model"] = targetModelName` before sending upstream (~line 455 of ProxyService.cs). When a chain resolves `tier1 → ["anthropic/claude-opus-4-5", ...]`, the first call sets `targetModelName = "claude-opus-4-5"` and that is what the upstream sees. The chain name `tier1` is never forwarded. ✓

### Circuit Breaker — No Changes Needed

Circuit state is keyed `"{providerId}::{modelName}"` (e.g. `"anthropic::claude-opus-4-5"`). The chain intercept resolves to real `providerId/modelId` entries before entering `ExecuteExplicitChainAsync`, so the per-entry circuit check in the waterfall loop (`GetCircuitStatus(targetProviderId, targetModelName)`) operates on the real coordinates. Chain name `tier1` never appears in circuit state keys. ✓

### `model_chains.json` Location

Default: `./model_chains.json` in the server working directory (same as `providers.json`). Override via `MODEL_CHAINS_CONFIG_PATH` env var (same pattern as `PROVIDERS_CONFIG_PATH`).

### AOT-Safe DTO Binding

`POST /api/model-chains` and `PUT /api/model-chains/{name}` receive JSON body. With Minimal APIs + AOT, body binding for named records works via the AOT-registered source generator context. The `[JsonSerializable]` entries added in Task 1.2 are sufficient — no additional `[FromBody]` or `AsParameters()` needed, as Minimal APIs resolve these automatically for registered types in AOT mode. Verify by running `dotnet build` — any unregistered type will emit a trimming warning.

### Frontend: API Key Header

All fetch calls to `/api/model-chains` must include `'X-Api-Key': $apiKeyStore` — same pattern as `ClaudeCodeConfig.svelte`. If a shared auth helper exists in `$lib/api.js` or similar, use it.
