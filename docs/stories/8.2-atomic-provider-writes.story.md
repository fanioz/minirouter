# Story 8.2: Atomic Provider Config Writes

## Description

Every provider CRUD operation re-serializes the entire provider list and overwrites
`providers.json` in place:

```csharp
await File.WriteAllTextAsync(_configPath, json);
```

at `Services/ProviderService.cs:176` (create), `:211` (update), and `:242` (delete). There is
no temp-file-and-rename, so a crash, kill, or container stop during the write truncates the
config — losing every configured provider and its credentials.

This closes **Story 1.3** from `epic-technical-debt.md`, which is marked `[x]` complete but
was never implemented. See the Baseline Correction section of `epic-capability-parity.md`.

Story 8.5 (SQLite migration) would have removed this problem entirely, but was **cut
(2026-08-11)** — so `providers.json` remains the persistence format and this fix is the
permanent solution, not a stopgap.

## Priority

0 (Wave 0 — closes Story 1.3; corruption window is open in production today)

## Implementation Steps

### 1. Extract a single write path

The three call sites currently duplicate the serialize-and-write sequence. Consolidate into
one private method so the atomicity guarantee exists in exactly one place:

```csharp
private async Task PersistAsync(List<Provider> providers, CancellationToken ct)
```

### 2. Write to temp, then rename

Within `PersistAsync`:
- Serialize to `{_configPath}.tmp` via `File.WriteAllTextAsync`
- Flush to disk before the rename — `WriteAllTextAsync` does not guarantee an fsync, and a
  rename of an unflushed file can still yield a truncated result after power loss
- `File.Move(tmpPath, _configPath, overwrite: true)` — atomic within the same filesystem

The temp file **must** sit in the same directory as the target. A temp path on a different
filesystem degrades `File.Move` into a non-atomic copy, reintroducing the bug.

### 3. Clean up orphaned temp files

If a previous run died between write and rename, a stale `.tmp` remains. On startup, delete
any orphaned `{_configPath}.tmp` — do not attempt recovery from it, since its contents may be
partial.

### 4. Preserve existing write serialization

`ProviderService` already guards writes with a `SemaphoreSlim`. Keep it — atomicity protects
against crash-mid-write, the semaphore protects against concurrent writers. Both are needed.

## Acceptance Criteria

- [x] All three CRUD paths route through a single `PersistAsync` method
- [x] The temp file is created in the same directory as `_configPath`
- [x] Content is flushed to disk before the rename
- [x] A stale `.tmp` file present at startup is removed and ignored
- [x] The existing `SemaphoreSlim` write serialization is retained
- [x] Provider CRUD behavior is otherwise unchanged — no API surface change

## Required Tests (QA)

- Unit: create/update/delete each produce a valid, fully-parseable `providers.json`
- Unit: a pre-existing orphaned `.tmp` at startup is cleaned up and does not corrupt load
- Concurrency: N parallel writes leave the file parseable with the final write's content
- Manual: `kill -9` the process during a write loop; confirm `providers.json` still parses

The kill-during-write check is the one that actually validates this story. The unit tests
confirm the happy path but cannot reproduce the failure mode being fixed.
