# Story 8.6: Anthropic Messages Protocol Translation

## Description

MiniRouter accepts exactly one inbound format: OpenAI Chat Completions. Every configured
provider must itself speak that protocol. This is the **only structural gap** in the 9Router
analysis — everything else is additive surface area, but translation changes what the router
fundamentally is: a same-protocol load balancer today, a translating gateway after this story.

Adding `POST /v1/messages` (Anthropic Messages) inbound, translated to OpenAI Chat Completions
outbound, unlocks Claude Code and every other Anthropic-format client against any
OpenAI-compatible upstream we already support.

Secondary benefit: it fixes a latent config trap. `providers.example.json` ships
`https://api.anthropic.com` as a sample provider, which MiniRouter would call at
`https://api.anthropic.com/v1/chat/completions` with a `Bearer` header. That is not the
Anthropic contract — the sample **cannot work as written**.

## Priority

3 (Wave 2 — highest leverage, but sequenced last because nothing else depends on it)

## Scope Discipline

The reference translator is 22 files with ~2,151 LOC in `concerns/` alone. We need **one
direction pair**, not the matrix.

**Port:**

| Reference file | LOC | Purpose |
|---|---|---|
| `translator/request/claude-to-openai.js` | 263 | Inbound request translation |
| `translator/response/openai-to-claude.js` | 265 | Outbound response translation |
| `concerns/toolCall.js` | 153 | Tool call ID and shape mapping |
| `concerns/finishReason.js` | 63 | `stop_reason` ↔ `finish_reason` |
| `concerns/usage.js` | 69 | Token field mapping |
| `concerns/image.js` | 124 | Base64 image block handling |

**Do not port:** `thinkingUnified.js` (353), `kiroConversation.js` (435), `modality.js`,
`prefetch.js`, `paramSupport.js`. None apply to a single Anthropic↔OpenAI pair.

Realistic C# target: **~800-900 LOC**, not 2,151.

Adopt the reference's **schema-enum discipline** (`translator/schema/`) — role, block type, and
finish reason as enums, never inline string literals. This is the single most valuable
structural idea to carry over; it is what keeps the mapping auditable.

**Do not** build the pivot abstraction. The reference pivots through OpenAI as an intermediate
format because it supports 13 formats. With one pair, a direct translator is simpler and
strictly less lossy. If a second inbound format is ever added, refactor then.

## Implementation Steps

### 1. Request translation (Anthropic → OpenAI)

- `system` (top-level string or block array) → a `system` role message prepended to `messages`
- Content blocks → OpenAI content: `text` passthrough, `image` → `image_url` with a base64 data
  URI, `tool_use` → `tool_calls`, `tool_result` → a `tool` role message
- `max_tokens` is **required** in Anthropic and optional in OpenAI — pass through; do not invent
  a default
- `stop_sequences` → `stop`
- Preserve `tool_use_id` ↔ `tool_call_id` correspondence exactly. Mismatched IDs are the most
  common failure mode in this class of translation and produce confusing downstream errors.

### 2. Response translation (OpenAI → Anthropic), non-streaming

- `choices[0].message.content` → a `content` array of blocks
- `tool_calls` → `tool_use` blocks
- `finish_reason` → `stop_reason`: `stop`→`end_turn`, `length`→`max_tokens`,
  `tool_calls`→`tool_use`
- `usage.prompt_tokens`/`completion_tokens` → `input_tokens`/`output_tokens`
- Emit the Anthropic envelope: `id`, `type: "message"`, `role: "assistant"`, `model`

### 3. Response translation, streaming — the hard part

Anthropic's event model does not map 1:1 onto OpenAI chunks. A single OpenAI delta stream must
be synthesized into an ordered Anthropic event sequence:

```
message_start
content_block_start   (index 0)
content_block_delta   (× N)
content_block_stop
message_delta         (carries stop_reason + output_tokens)
message_stop
```

Requirements:
- Each event needs both an SSE `event:` name and a `data:` payload — Anthropic clients dispatch
  on the event name
- Tool calls arrive incrementally in OpenAI (`function.arguments` fragments) and must accumulate
  into `input_json_delta` events under the correct block index
- `message_delta` carries the terminal `stop_reason` and output token count, which are only
  known at stream end

**Two blockers in the existing SSE path must be fixed first:**

1. `Services/ProxyService.cs` re-emits SSE lines with `"\n"` rather than the `"\n\n"` event
   terminator. The Svelte dashboard's parser tolerates this; Anthropic clients will not.
2. `Services/ProxyService.cs:82-83` sets `StatusCode`/`ContentType` after the body has started
   (gap analysis defect 3). Streaming translation cannot be built on a path that throws at the
   end of every successful stream.

Fix both as part of this story.

### 4. Endpoint wiring

- `POST /v1/messages`, behind `ApiKeyEndpointFilter` like `/v1/chat/completions`
- Same `providerId/modelName` explicit routing and comma-separated fallback (Story 7.1)
- Errors translated to Anthropic error shape (`type: "error"`, nested `error.type`/`message`),
  not passed through as OpenAI errors

### 5. Token counting endpoint

`POST /v1/messages/count_tokens` — Claude Code calls this. Reuse the estimator from Story 8.4
(~4 chars/token) and label the response as approximate. An accurate count would require the
upstream tokenizer, which we do not have.

## Required Tests (QA)

- Request translation: system forms, content blocks, images, tool_use, tool_result, stop_sequences
- Response translation non-streaming: content, tool_calls, all `stop_reason` values, usage
- Streaming: full event sequence order, incremental tool-call accumulation, terminal
  `message_delta`, `\n\n` framing
- Tool ID correspondence across a 3-turn conversation
- Error shape translation for 400 / 401 / 429 / 502
- Regression: existing `/v1/chat/completions` streaming and non-streaming unaffected
- **End-to-end with a real Anthropic-format client** — the only test that meaningfully validates
  this story. Unit tests confirm shape; they do not confirm a client accepts the stream.

## Notes on the Estimate

**40h is the least reliable number in Epic 8.** It was sized from reference LOC, which is a weak
proxy for effort. Streaming event-model translation is where this class of work overruns.

Recommend a **1-day spike on the streaming path alone** before committing the full wave — build
`message_start` → `content_block_delta` → `message_stop` against a real client, confirm framing
is accepted, then firm up the remaining estimate.

**AOT cost is unmeasured.** The Anthropic message schema is substantially larger than anything
currently in `AppJsonContext` (`Models/Provider.cs:63-88`), and every type registered there is
compiled weight. Epic success criteria include idle RSS < 50 MB. Measure after this story rather
than discovering the cost at the end.

Prefer `JsonNode` manipulation over fully-typed models where the shape is passthrough. Typed
records for every Anthropic block variant would inflate the JSON context for little benefit.
