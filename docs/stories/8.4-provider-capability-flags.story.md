# Story 8.4: Per-Provider Capability Flags

## Description

MiniRouter injects `stream_options: {include_usage: true}` into **every** outgoing streaming
request to capture token usage (`Services/ProxyService.cs:237-252`). The `README.md:285-296`
known-issues block flags this as unverified and potentially unsafe: reference analysis of
9Router shows some providers reject the field outright (observed with Codex and Grok-CLI-style
providers), which fails the request entirely.

This story closes that known issue by replacing global injection with a per-provider capability
flag, plus an estimator fallback for providers that legitimately return no usage.

The reference does not solve this by detection or probing — it declares provider quirks as
static data in the registry and estimates when usage is absent. We adopt the same shape at a
much smaller scale: a few flags on our existing generic `Provider` record, rather than 119
registry files.

## Implementation Steps

### 1. Add capability fields to `Provider`

Extend the record (`Models/Provider.cs:5-13`) with nullable flags so existing
`providers.json` files keep working unchanged:

```csharp
bool? SupportsStreamOptions = null,   // null = assume true, inject
bool? ReportsStreamUsage  = null      // null = assume true, no estimate
```

Null-as-default matters: every currently-deployed config must load and behave identically
until an operator opts in. Propagate to `CreateProviderDto`, `UpdateProviderDto`, and
`MaskedProvider`.

### 2. Gate the injection

At `Services/ProxyService.cs:237-252`, inject `stream_options.include_usage` only when
`SupportsStreamOptions != false`. When explicitly `false`, leave the request body untouched.

The existing suppression logic — which strips the usage-only chunk or the `usage` field when
the flag was injected rather than client-requested (`ProxyService.cs:401-416`) — stays as is.
It is already conditioned on `injectedIncludeUsage`, so a non-injecting path skips it correctly.

### 3. Add a token estimator fallback

Port the approximation from `docs/reff/open-sse/utils/usageTracking.js`: roughly **4 characters
per token**.

Apply only when a streaming response completed successfully **and** yielded no usage data —
either because injection was suppressed or because the provider ignored the flag. Estimate
prompt tokens from the outbound request body and completion tokens from the accumulated
response text.

Log rows must distinguish estimated from reported values. Without that flag, cost calculation
(Story 8.7) would silently mix measured and guessed numbers, and nobody downstream could tell.
Add an `estimated` boolean to `RequestLog` and the `request_log` table.

### 4. Surface the flags in the dashboard

Add both toggles to the provider create/edit dialog in `frontend/src/Providers.svelte`, with
help text explaining that they are compatibility workarounds, not performance settings.

## Acceptance Criteria

- [ ] An existing `providers.json` with no capability fields loads and behaves exactly as today
- [ ] `SupportsStreamOptions: false` produces an outbound body with no `stream_options` added
- [ ] `SupportsStreamOptions: true` or null injects as before
- [ ] A successful stream yielding no usage produces an estimate rather than zeros
- [ ] Estimated rows are marked `estimated = true` in `request_log`; reported rows are `false`
- [ ] Client-supplied `stream_options.include_usage: true` is still honored and never suppressed
- [ ] Both flags are editable in the dashboard and round-trip through the CRUD API
- [ ] `README.md` known-issues block is updated to reflect the fix

## Required Tests (QA)

- Backward compatibility: a config with no capability fields deserializes with nulls
- Injection gating: `false` omits the field, `true`/null injects
- Suppression: injected usage chunk is stripped; client-requested usage passes through
- Estimator: fires only on zero-usage success, not on failure, and not when usage was reported
- Estimator accuracy: within a reasonable band on a known fixture (this is an approximation —
  assert order of magnitude, not exact counts)
- `estimated` flag correctly set on both paths

## Notes

The estimator is deliberately crude. The reference adds a 2000-token buffer to prevent
client-side context errors; that buffer is appropriate when the estimate feeds back into a
context-limit decision, but **not** here, where the number lands in a log row and later a cost
figure. Inflating logged usage by 2000 tokens per request would badly distort cost reporting.
Port the 4-chars-per-token ratio; do **not** port the buffer.

New serialized fields require `AppJsonContext` registration (`Models/Provider.cs:63-88`).
